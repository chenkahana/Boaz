# S2 Chrome style and native controls

Status: IN PROGRESS. No extension-parity or complete hosting verdict yet.

Selected CEF source: `57389f04a61ab0e9603d9f96602843d0e08bb11c`, standard arm64 CEF 156.0.28. [The pinned macOS header](https://github.com/chromiumembedded/cef/blob/57389f04a61ab0e9603d9f96602843d0e08bb11c/include/internal/cef_types_mac.h#L150-L155) forces Alloy when a parent NSView is supplied. S2a therefore uses CEF Views ownership rather than setting Chrome style on a native child browser.

## Verified source constraints

[The runtime contract](https://github.com/chromiumembedded/cef/blob/57389f04a61ab0e9603d9f96602843d0e08bb11c/include/internal/cef_types_runtime.h#L53-L57) permits one Chrome-style BrowserView per CefWindow. [The implementation](https://github.com/chromiumembedded/cef/blob/57389f04a61ab0e9603d9f96602843d0e08bb11c/libcef/browser/views/browser_view_impl.cc#L317-L345) rejects a second fresh Chrome BrowserView. Arbitrary reparenting of an existing view does not establish supported browser/widget ownership.

[ChromeBrowserHostImpl](https://github.com/chromiumembedded/cef/blob/57389f04a61ab0e9603d9f96602843d0e08bb11c/libcef/browser/chrome/chrome_browser_host_impl.cc#L99-L109) distinguishes the single browser in a Views-hosted window from the multiple tabs in an ordinary Chrome-hosted window. Do not assume Chrome's tab strip model automatically implements Boaz's independent page views.

## Bounded runtime sequence

1. One Chrome CefWindow/BrowserView, with no Chrome toolbar. Reserve native sidebar and toolbar space using Views layout; add SwiftUI hosting views as native siblings. Confirm actual runtime style, content, focus, resize, and lifecycle.
2. Retain two independent Chrome window/browser pairs and switch their visibility without reload. Check page state, browser identifiers, and extension targeting.
3. For split mode, investigate a frameless second Chrome window using the supported `GetParentWindow` API. Confirm clipping, focus, divider sizing, fullscreen, Mission Control, Stage Manager, extension window semantics, and close behavior.

Separate windows are a candidate experiment, not an accepted product architecture. A successful single-view experiment does not establish tab or split parity. If the result cannot meet native behavior, evaluate S2b within its 300-line CEF-only patch limit after the custom build is available.

## Single-page runtime evidence

The arm64 Release prototype built against the pinned distribution. Native inspection on 2026-11-13 confirmed the actual Chrome runtime, visible local and HTTPS content, working SwiftUI navigation controls, page input, and resizing to 1920 pixels wide while retaining page position and input.

SwiftUI controls inside Chromium's native root initially rendered but did not receive clicks or appear in accessibility. A plain NSView wrapper now contains that unchanged root and native SwiftUI siblings. Chromium's pinned `bridged_content_view.mm` overrides root hit testing and accessibility, and explicitly adjusts event coordinates when its root is not the window content view. The root frame must be set after insertion because `viewDidMoveToWindow` resets it. No CEF source patch was used.

Window-button close completed `OnBeforeClose`, `CefShutdown`, and process exit 0. Cmd+Q dispatched Chrome `IDC_EXIT`, bypassing native `terminate:`. Routing that named command through the existing close lifecycle also completed shutdown and exit 0 in a controlled run. An earlier run hit the shutdown watchdog while the UI inspection tool automatically relaunched the same profile; causation is unproven. Repeated-launch stability remains pending.

Verdict: single-page host evidence only. Accessibility-tree exposure does not establish VoiceOver behavior. Extensions, multiple retained pages, split view, fullscreen, Stage Manager, Mission Control, remaining shortcuts, signing and notarization remain required gates.

Follow-up native checks: the green window button entered fullscreen with correct native/sidebar/page layout. Ctrl+Cmd+F and Escape did not leave fullscreen; shortcut parity remains failed. A later controlled relaunch with no UI-tool auto-relaunch again hit the shutdown watchdog after `OnBeforeClose`. Shutdown stability therefore remains failed, despite individual exit-0 runs. Do not attribute all failures to the inspection tool. See [extension evidence](extensions.md) for the real MV3 probe.

The [development-signing follow-up](signing.md) passed two launches and clean shutdowns with a fresh signed-only profile. Old ad-hoc profile failures remain recorded rather than erased. The diagnostic Chrome toolbar now proves a real extension popup and content-script action on the visible page. The final toolbar-free native extension route is still unresolved; these results do not approve production integration.
