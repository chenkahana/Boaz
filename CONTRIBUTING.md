# Contributing to Folio

Thanks for helping make Folio better. This guide covers how to report problems, propose changes and get a pull
request merged.

## Before you start

- **Bugs and ideas** go in [GitHub Issues](https://github.com/chenkahana/Folio/issues/new/choose). Search first; add
  to an existing issue rather than opening a duplicate.
- **Security issues** must not be filed publicly. Follow [SECURITY.md](SECURITY.md).
- **Larger changes** (new features, new dependencies, schema or sync changes) need an issue agreed with a maintainer
  before you write the code.

By opening a pull request you confirm that you wrote the change, or have the right to submit it, and you grant the
copyright holder a perpetual, irrevocable, worldwide, royalty-free license to use, modify and distribute it as part
of Folio under any terms.

## Development setup

```bash
make bootstrap
```

Then open `Folio.xcodeproj`. Requirements, schemes and common commands are in the
[README](README.md#getting-started). The Xcode project is generated by XcodeGen from `project.yml`: edit
`project.yml`, never the generated project, and run `make project` afterwards.

## Branches and commits

- `master` is always releasable. Work on a branch named `<type>/<short-description>`, e.g. `fix/sync-tombstones`.
- Write commit subjects in the imperative mood, under 72 characters ("Fix duplicate tabs after an Arc import").
  Explain *why* in the body when it isn't obvious.
- Keep a pull request to one concern. Refactors go in their own pull request.
- Add follow-up commits to an open pull request instead of force-pushing; it is squashed when merged.

## Code guidelines

- **Swift 6, strict concurrency.** App targets default to `@MainActor`. Keep database, sync and file work off the
  main actor (`FolioStore`'s async API); the UI must never wait on SQLite or the network.
- **Shared logic lives in FolioKit.** Anything both apps need (model, persistence, sync, import) belongs in
  `Packages/FolioKit`, not in an app target.
- **SwiftUI first.** Use UIKit/AppKit only where SwiftUI has no equivalent, and keep it behind a small
  representable.
- **Schema changes** need a new migration in `FolioStore`; never edit a shipped migration. If a change alters synced
  records, update `SyncMapping` and keep older clients working.
- **Privacy.** Don't add analytics, tracking or third-party SDKs that collect data. Anything new that leaves the
  device must be reflected in [docs/privacy.md](docs/privacy.md) and `Apps/Shared/PrivacyInfo.xcprivacy`.
- **Accessibility.** Every control needs a VoiceOver label, works with Dynamic Type and respects Reduce Motion.
- **Comments** explain intent and constraints, not what the next line does.

## Checks before you open a pull request

```bash
make build
```

- Run the app you changed: iPhone Duo simulator for iOS (folded and unfolded), and the Mac app.
- If you touched sync, check two devices or simulators signed in to the same iCloud account.
- Fill in the pull request template, including screenshots or a recording for UI changes.

CI builds FolioKit and both apps on every pull request; it must pass before review.
